# LoRA versus full-parameter online RL for ACE-Step-style DiTs

## Bottom line

LoRA is not inherently negligible, and “LoRA works” is not evidence of parity with full-parameter RL. The strongest direct comparisons are currently in language-model RL and disagree in important ways: one controlled study reports LoRA matching full fine-tuning down to rank 1 when all matrices and learning rates are chosen carefully; another reports standard LoRA below full fine-tuning and a clear rank/expressivity floor. Flow-matching and diffusion papers show that LoRA can support effective online RL, but their headline experiments are LoRA-only, not LoRA-versus-full controls. Audio diffusion evidence is even thinner: the available RL paper compares objectives, not adapter regimes.

Therefore, no current primary source proves that LoRA and full DiT RL are equivalent for ACE-Step music. ACE-Step’s own report describes intrinsic RL on the DiT, but its published benchmark is explicitly “dynamic distilled DiT (no RL),” and the current model-zoo table marks all released DiT variants as RL-unsupported. The question should be settled by a matched ACE ablation.

## ACE-specific implementation facts and limits

The current ACE LoRA injector scans the DiT decoder for `q_proj`, `k_proj`, `v_proj`, and `o_proj` only ([source](https://raw.githubusercontent.com/ACE-Step/ACE-Step-1.5/main/acestep/training/lora_injection.py)); its default is rank 8, alpha 16, dropout 0.1 ([config](https://raw.githubusercontent.com/ACE-Step/ACE-Step-1.5/main/acestep/training/configs.py)). The V2 loader freezes all parameters by default, loads the VAE and Qwen3 embedding encoder for preprocessing, and puts them in eval mode ([loader](https://raw.githubusercontent.com/ACE-Step/ACE-Step-1.5/main/acestep/training_v2/model_loader.py)). This supports the intended online-RL isolation: freeze VAE/text/condition encoders and update only the DiT decoder.

ACE’s [large-scale training guide](https://github.com/ACE-Step/ACE-Step-1.5/blob/main/docs/en/Large_Scale_SFT_Training_Guide.md) is SFT guidance, not RL evidence. It contrasts rank-128 LoRA (~50M trainable parameters) with a full decoder (~3.5B), gives rough per-GPU figures of 20–30 GB versus 60–80 GB, and says full-parameter SFT is not natively supported. These numbers should not be presented as measured online-RL memory or as a quality result.

For a 2B DiT, a separate static-memory estimate is useful but approximate: bf16 weights are about 4 GB; bf16 gradients about 4 GB; Adam fp32 first/second moments about 16 GB; and an optional fp32 master copy about 4 GB. Thus roughly 24–32 GB is a plausible full-decoder parameter/optimizer floor before activations, attention workspaces, rollout/reference-policy copies, VAE, and framework overhead. Precision, optimizer, sharding, checkpointing, and reference-policy layout can move this substantially. It is an estimate, not an ACE benchmark.

Freezing the VAE is appropriate for isolating the DiT question, but it creates an important ceiling: a full DiT update cannot change the codec's reconstruction map or bandwidth capacity. It may reduce some artifacts by moving probability toward better-decoding latents, but it cannot be assumed to eliminate errors imposed by the fixed codec. Evaluate VAE reconstructions separately so a decoder-versus-adapter conclusion is not confused with this constraint.

## Recommended ACE ablation

Hold one ACE variant fixed (base, SFT, or turbo; do not mix 50-step and 8-step variants), one reward definition, and one online FM-RL algorithm. For every arm, freeze VAE, text encoder, condition encoders, and all non-decoder modules; precompute/hold their latents and embeddings where possible.

1. **Full decoder:** all DiT decoder weights trainable.
2. **All-module LoRA:** decoder attention plus MLP projections (`q/k/v/o` and `gate/up/down`) at ranks 8, 32, and 128. Keep the effective scale comparable, e.g. alpha = 2×rank, and record exact trainable parameter counts.
3. **Attention-only control:** decoder `q/k/v/o`, rank 32. This isolates module coverage from rank and tests the attention-only failure mode reported in the LLM studies.
4. **Optional matched-capacity control:** if the native injector cannot target MLP names, add an explicit MLP-target implementation or choose rank(s) so attention-only and all-module arms have the same trainable-parameter budget. Do not call different parameter counts a rank comparison.

Use the same prompt/audio split, rollout RNG protocol, solver, train/eval denoising steps, group size, reward normalization, number of generated trajectories, optimizer-update count, batch/accumulation, and checkpoint cadence. Run independent LR sweeps for FullFT and each LoRA family; the roughly 10× LoRA LR seen in LLM work is a starting prior, not an ACE rule. Keep alpha/r fixed when sweeping rank. Use multiple seeds if feasible.

Report two views:

- **Matched sampling/update budget:** equal rollout queries, groups, denoising steps, and optimizer updates. Plot reward/AAS versus rollout count and update count.
- **Matched resource budget:** equal wall-clock/GPU-hours or measured training FLOPs. Report how many rollouts/updates each arm buys, peak VRAM, throughput, and checkpoint size. Do not mix this conclusion with the sample-matched result.

Track held-out AAS and any independent lyric/frame alignment score, prompt/style adherence, audio quality and diversity measures, lyric intelligibility/timing, reward-hacking indicators, and regression from the base model. Include VAE reconstruction quality and fixed-VAE decode tests. A LoRA result near FullFT would demonstrate parity only for the selected ACE variant, reward, solver, and budget; a gap should be diagnosed by rank, module coverage, LR, optimizer, or reward/codec limits rather than attributed to “LoRA” in the abstract.
